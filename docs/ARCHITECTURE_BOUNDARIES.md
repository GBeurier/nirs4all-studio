# Architecture Boundaries

This document is the short operational contract for keeping Studio maintainable while the dag-ml backend, multimodal data model, cluster execution, and WASM-oriented runtime evolve.

For the full audit and migration roadmap, see [STUDIO_PRISTINE_AUDIT.md](STUDIO_PRISTINE_AUDIT.md).

## Backend Route Ownership

- `api/workspace/router_*.py` owns global workspace resources and user configuration: linked datasets, workspace groups, linked workspaces, app settings, favorites, and custom nodes.
- `api/datasets.py` owns dataset interpretation services: detection, validation, preview, loading, stats, verification, synthetic presets, and folder scanning.
- `api/pipelines.py` owns persisted pipeline definitions and editor-facing pipeline operations.
- `api/runs.py` owns run lifecycle, execution status, logs, artifacts, cancellation, and additive `execution_backend` metadata (`local-python`, `cluster`, `wasm-local`) until cluster/campaign submission is split into a dedicated execution adapter layer.
- `api/run_execution_plan.py` owns explicit backend legacy run-plan construction: dataset x pipeline entries, split-grouping propagation, variant expansion metadata, and total pipeline-run counts. Keep this planning layer testable so future campaign/cluster execution can replace the legacy cartesian plan without expanding `api/runs.py`.
- `api/models.py` owns trained model inventory and model artifact operations.
- `api/native_results_adapter.py` owns deterministic identity rules for fallback native n4a results: module-level `_native_base_config`, `_native_chain_id`, and `_native_prediction_id` define stable base-config normalization, `_refit` folding, chain ids, and prediction ids. Keep these rules module-level and directly testable for future n4a-repo/native results access; `NativeResultsAdapter` static wrappers remain compatibility shims around them, not the long-term policy owner.
- `api/inspector.py` owns Inspector HTTP routes, request/response models, store access, and chart/diagnostic endpoint orchestration. Keep chain-row normalization, JSON-like metadata parsing, task-family filtering, preprocessing label splitting, pipeline metadata enrichment, and numeric hyperparameter flattening in `api/inspector_normalization.py` so future benchmark/repository/SHAP/Optuna result sources can share one policy outside route code.
- `api/pipeline_canonical.py` owns backend canonical/editor conversion orchestration and compatibility re-exports. Keep finetune/search-space conversion in `api/pipeline_canonical_finetune.py`, generator conversion in `api/pipeline_canonical_generators.py`, and branch/merge conversion in `api/pipeline_canonical_branch_merge.py` before future Optuna, train-param, dag-ml, source/repetition branching, or backend-specific pipeline schema changes.

Do not expose the same public `method + path` from multiple routers. Add a new route only after checking the existing owner and run `npm run test:routes` when route ownership changes.

- `tests/test_route_registry.py` guards public FastAPI route uniqueness and dataset-route ownership. Keep `/api/datasets` list/link/unlink/refresh in `api.workspace.router_datasets`, and keep dataset interpretation/preview/load/stats/verify routes in `api.datasets`; update the route registry test before moving ownership.

## Frontend Domain Boundaries

- `src/api/` contains transport wrappers only. It should not contain UI normalization, cross-page orchestration, or backend fallback policy.
- `src/lib/` contains pure domain adapters, schema normalization, compatibility layers, and reusable calculations.
- `src/lib/sessionPersistence.ts` owns generic timestamped session persistence: JSON read/write, expiration, storage clearing, storage errors, and optional migration hooks. Feature-specific session modules should wrap it and should receive a `clientStorage`-backed storage adapter from providers instead of reading browser storage directly.
- `src/hooks/` coordinates data fetching and UI state for one bounded workflow.
- `src/context/` is for shared application state that truly crosses page boundaries. Provider `.tsx` files should export provider components only; shared hooks/context objects belong in sibling `.ts` modules such as `useMlReadiness.ts` to keep Fast Refresh clean.
- `src/components/` contains reusable UI primitives and bounded feature components. Large workflow pages should compose feature components instead of owning their full UI tree directly.
- `src/pages/` wires routes, page-level layout, and feature orchestration. Pages should not become the long-term home for dataset, pipeline, run, or inspector business logic.
- `src/components/layout/BackendStartupBannerData.ts` owns pure backend-startup banner read models: workspace fetch phase, settle eligibility, title/description translation tokens, raw error description selection, progress value, badge icon/label choice, and per-step label/detail/state models. Add future WASM readiness, cluster connection, cache warmup, or repository sync startup phases here before growing `BackendStartupBanner.tsx`.
- `src/components/layout/FloatingRunWidgetData.ts` owns pure floating-run-widget read models: route visibility, selected-run fallback, minimized badge count, run item labels/classes, recent-log slicing, detail navigation path, and display flags for selectors, summaries, and logs. Add future campaign/cluster task grouping, remote-run summaries, and active-run priority rules here before growing `FloatingRunWidget.tsx`.

## Target Domain Split

The next backend generation should be integrated behind stable frontend domains:

- `datasets`: multimodal source discovery, schemas, dataset previews, target definitions, fold/refit aggregation previews, and nirs4all-io/nirs4all-formats compatibility.
- `pipelines`: dag-ml graph definition, operator registry, backend capability selection, schema contracts, and one-pipeline/one-dataset validation.
- `campaigns`: reusable execution plans that replace the current simple cartesian `n pipelines x m datasets` mental model when preview, cluster scheduling, and run cardinality matter.
- `runs`: local and remote execution state, cluster task mapping, artifacts, logs, and reproducibility metadata.
- `results`: predictions, metrics, benchmark metadata, SHAP/Optuna outputs, comparisons, and meta-analysis.
- `repository`: n4a-repo access, remote assets, imports, exports, and provenance.

Each domain should expose typed frontend contracts before large UI work starts. UI components should consume those contracts rather than raw backend payloads.

## Client Storage Contracts

- `src/lib/clientStorage/keyRegistry.ts` owns the browser-storage key catalog: key strings, storage area, scope, version, and ownership description, including Playground/Inspector session keys, current edited-pipeline handoff, and dynamic pipeline-editor draft keys. Add future WASM/web/Electron storage scopes, workspace-scoped keys, and migration metadata here before introducing new `localStorage` or `sessionStorage` keys in components.
- `src/lib/clientStorage/store.ts` owns safe browser-storage access: SSR/restricted-storage guards, raw string reads/writes, raw JSON reads/writes, versioned JSON reads/writes, removals, area clears, and `createClientStoragePersistenceStorage()` for adapting registered keys to timestamped session persistence. UI modules should consume this facade instead of catching storage errors locally.
- `src/lib/clientStorage/migrations.ts` owns the optional versioned-record envelope and migration dispatch helpers. Keep legacy raw-value compatibility here so existing user preferences and draft/cache formats remain readable while new storage families gain explicit versions.
- `src/lib/clientStorage/index.ts` is the stable import facade for frontend storage helpers. Keep direct `localStorage` / `sessionStorage` access limited to this module family.

## Extension Rules

- Add compatibility adapters at the domain boundary, not inside visual components.
- Keep feature flags and backend capability detection centralized; do not branch deeply inside pages.
- Prefer schema-backed previews before execution for any dataset/pipeline feature that can change run cardinality, transformations, targets, or artifacts.
- Treat cluster execution as a run backend, not as a separate UI workflow.
- Treat Optuna and SHAP as pipeline-level result producers, not model-only side panels.
- Keep WASM constraints visible: pure data contracts, no hidden filesystem assumptions in shared frontend code, and no Python-specific types leaking into reusable UI state.
